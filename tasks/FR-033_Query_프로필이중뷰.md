## 🎯 Summary
- 기능명: **[FR-033] 남이 보는 내 프로필에는 비공개 기록의 흔적조차 없다**
- 목적: **REQ-NF-009의 가장 어려운 조항 — "건수·존재 여부를 유추할 수 있는 정보를 반환해서는 안 된다"를 만족한다.**

> 🔴 **"안 보여준다"와 "없는 것처럼 보인다"는 다르다.**
>
> REQ-NF-009: *"권한 없는 자원은 **응답에서 완전히 제외**해야 하며, **건수·존재 여부를 유추할 수 있는 정보를 반환해서는 안 된다**."*
>
> 흔한 구현은 목록만 거르고 **개수는 전체로 센다.** 그러면 *"기록 27개"* 인데 3개만 보이는 프로필이 나오고, **비공개 기록이 24개 있다는 사실이 노출된다.** SC-4.4가 정확히 이 지점을 검사한다.
>
> 🟢 **RLS가 이 문제를 구조적으로 푼다** — `count(*)` 도 정책의 영향을 받으므로 **애플리케이션이 따로 신경 쓸 필요가 없어진다.**

## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 타인에게는 전체공개만 보인다** *(SC-4.4)*
- **Given**: 전체공개 3건 · 그룹 5건 · 비공개 19건인 사용자
- **When**: 완전한 타인이 프로필을 봄
- **Then**: **3건만 보인다**

**Scenario 2: 개수도 3이다** *(REQ-NF-009 · SC-4.4)*
- **Given**: 위와 같은 상황
- **When**: 기록 수를 확인함
- **Then**: 🔴 **"3"이다.** *"27"* 이나 *"3 / 27"* 이 아니다. **개수 하나가 비공개 24건의 존재를 알려준다**

**Scenario 3: 그룹 구성원에게는 그룹 기록도 보인다**
- **Given**: 같은 그룹의 구성원이 조회함
- **When**: 프로필을 봄
- **Then**: **전체공개 3 + 그룹 5 = 8건**이 보이고 개수도 8이다

**Scenario 4: 팔로워라고 더 보이지 않는다** *(규칙 8)*
- **Given**: 팔로워지만 같은 그룹이 아닌 사용자
- **When**: 프로필을 봄
- **Then**: 🔴 **전체공개 3건만.** 팔로우는 가시성을 바꾸지 않는다

**Scenario 5: 본인에게는 전부 보인다**
- **Given**: 자기 프로필
- **When**: 조회함
- **Then**: **27건 전부**. 소유자 조건이 RLS 정책에 포함돼 있다

**Scenario 6: 조작된 요청이 통하지 않는다** *(SC-4.F1)*
- **Given**: 비공개 기록의 ID를 직접 지정한 요청
- **When**: 조회를 시도함
- **Then**: 🔴 **우회 성공 0건**이고 **`visibility_denied` 감사 로그가 남는다.** 기록률 **100%**

**Scenario 7 (실패): 애플리케이션에서 세지 않는다**
- **Given**: 집계 구현
- **When**: 코드를 확인함
- **Then**: 🔴 **`count(*)` 가 RLS가 적용된 쿼리로 실행**된다. **애플리케이션에서 전체를 가져와 필터링 후 세는 구현은 성능도 나쁘고 반드시 새어나간다**
