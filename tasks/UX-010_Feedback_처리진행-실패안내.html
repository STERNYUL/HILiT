🎯 Summary

  • 화면명: [UX-010] 처리 진행과 실패 — 기다리는 8분과 실패하는 순간
  • 목적: 비동기 처리의 대기와 실패를 사용자가 견디고 이해할 수 있게 만든다.

🔴 이 화면이 실패 시나리오 11건의 종착지다.

SRS의 운영 시나리오 42건 중 실패 경로(SC-*.F*)가 11건인데, 그중 대부분이 이 화면에서 사용자와 만난다. 실패 처리를 잘 만들어도 화면이 없으면 사용자에게는 그냥 멈춘 것이다.

🔴 그리고 실패의 종류가 다르면 사용자가 할 일도 다르다 — CAPTURE(못 찾음)는 재지정, INFRA(장애)는 재시도. 같은 화면으로 처리하면 사용자가 헛수고를 한다.

🧪 설계 인수 기준

항목 1: 8분을 견딜 수 있다 (REQ-NF-003)

  • 🔴 지금 무슨 단계인지 · 얼마나 남았는지가 보인다. 막대 하나만 도는 화면으로는 8분을 견딜 수 없다

항목 2: 앱을 닫아도 된다고 말한다 (§6.5.3 · T1의 이득)

  • 🔴 탐지는 외부에서 돌므로 앱을 닫아도 계속된다. 이 사실을 알리지 않으면 사용자는 8분간 화면을 지켜본다 — 그러다 이탈한다

항목 3: 렌더는 다르다는 것을 구분해 알린다 (R1 · §6.5.3)

  • 🔴 렌더 중에는 이탈하면 소실된다. 같은 "처리 중" 화면으로 두 단계를 표현하면 안내가 서로 모순된다

항목 4: 못 찾음과 장애가 다른 화면이다 (SC-1.F2 vs SC-3.F1)

  • 🔴 CAPTURE 는 재지정, INFRA 는 재시도. 재시도 버튼을 CAPTURE 에 붙이면 같은 결과가 나오고 비용만 든다

항목 5: 후보가 적은 이유가 전달된다 (SC-1.F6)

  • 🔴 "28개는 확신이 낮아 제외했다"가 전달된다. 이유 없이 짧은 목록은 탐지 실패로 읽히고 사용자는 헛되이 재지정한다

항목 6: 실패해도 잃은 것이 없음을 알린다 (SC-3.F1)

  • 🔴 "선택은 그대로 있고 원본도 남아 있다"가 전달된다. 이 문장이 없으면 사용자는 처음부터 다시 해야 한다고 믿고 포기한다

항목 7: 재시도 소진이 막다른 길이 아니다

  • 🔺 3회 후 무엇을 할 수 있는지가 있다. 아무 안내 없이 끝나면 완주율(≥95%)이 여기서 떨어진다

항목 8 (경계): 가짜 진행률을 만들지 않는다

  • 🔺 stage 는 이산값이다. 실제 진행을 모르면서 매끄럽게 차오르는 막대를 만들면 거짓말이 된다. 단계 표시가 정직하다

⚙️ 설계 제약

  • 🔴 단계별 소실 범위가 다르다 — 업로드(중단·재개) · 탐지(영향 없음) · 선택(서버 복원) · 렌더(소실). 네 경우의 안내가 각각 달라야 한다
  • 🔴 실패 유형이 사용자 행동을 결정 — failure_class 가 화면 분기의 기준이다
  • 🔺 진행률 산출 근거가 [TBD] — FR-036과 공유하는 미결
  • 🔺 예상 시간 표시가 [PROPOSED] 값에 의존 — p95 8분은 확정치가 아니다. 틀린 예상은 없느니만 못하다
