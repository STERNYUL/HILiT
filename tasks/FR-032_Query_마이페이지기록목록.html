🎯 Summary

  • 기능명: [FR-032] 내 기록이 쌓인 것을 내가 본다
  • 목적: Gate B(기록 공간 수용성)가 판정할 대상, 즉 "기록 공간" 그 자체를 만든다.

🔴 이 화면이 D4의 결과물이다.

앞의 모든 태스크는 "공개하지 않아도 기록이 남는다" 를 가능하게 했다. 이 화면은 그 기록이 쌓인 것을 사용자가 실제로 보는 유일한 자리다. Gate B가 판정하는 것은 기술이 아니라 이 화면이 주는 느낌이다.

🔺 그래서 "목록이 나온다"만으로는 이 태스크가 끝나지 않는다 — SC-6.4(D30 기록 3편 이상 코호트)가 이 화면의 실질 지표다.

🧪 Acceptance Criteria (BDD/GWT)

Scenario 1: 비공개 기록이 내게는 보인다 (D4)

  • Given: private 기록 12건
  • When: 마이페이지를 엶
  • Then: 🔴 12건이 전부 보인다. 소유자 뷰에서는 공개 범위가 가시성을 제한하지 않는다

Scenario 2: 공개 범위가 배지로 표시된다 (SC-4.3 · ADR-4)

  • Given: 세 가지 범위가 섞인 목록
  • When: 격자를 확인함
  • Then: 🔴 글자 배지로 표시되고 영상을 가리지 않는다

Scenario 3: 종목·공개 범위로 거를 수 있다 (SC-4.5)

  • Given: 여러 종목의 기록
  • When: 필터를 적용함
  • Then: 해당 조건의 기록만 남는다. 두 필터를 함께 적용할 수 있다

Scenario 4: 날짜별로 쌓인 것이 보인다 (REQ-FUNC-020)

  • Given: 3개월간의 기록
  • When: 타임라인 뷰를 봄
  • Then: 날짜별 축적이 확인된다. 🔴 "쌓였다"는 감각이 Gate B의 판정 대상이다

Scenario 5: 400ms 안에 응답한다 (REQ-NF-005)

  • Given: 기록이 많은 계정
  • When: 목록을 조회함
  • Then: p95 ≤ 400ms. 🔺 RLS 정책이 걸린 쿼리의 성능을 인덱스로 받쳐야 한다(CT-001)

Scenario 6: 원본이 삭제된 기록도 보인다 (FR-004)

  • Given: 원본을 지운 기록
  • When: 목록을 봄
  • Then: 🔴 정상 표시되고 재생된다. source_video_id 가 NULL 이어도 기록은 온전하다

Scenario 7 (실패): 타인 뷰 로직을 이 함수에 섞지 않는다

  • Given: 프로필 조회 요구
  • When: 구현을 검토함
  • Then: 🔴 FR-033이 별도로 담당한다. 한 함수에 if (isOwner) 분기를 넣으면 SC-4.4(개수에도 미포함)를 실수로 깨뜨리기 쉽다
