1. 🔴 자동재생 음소거 — 목록에서 가장 무겁다

무엇이 문제인가

브라우저는 사용자 조작 없는 소리 있는 자동재생을 차단한다. 음소거 자동재생만 허용된다. 앱 진입 시 팔로잉 탭에서 바로 재생하려면(REQ-FUNC-011 · SC-6.1) 음소거로 시작할 수밖에 없다.

왜 이것이 심각한가

음악은 이 제품에서 부가 기능이 아니다.

근거내용
VPS 0.3F18을 F18a로 쪼개 MVP에 넣은 이유 — "음악이 없으면 사용자는 완성본을 CapCut·릴스로 내보내 붙이고, 그 순간 기록도 그쪽에 남는다"
SRS REQ-FUNC-0075갈래 500곡 자체 라이브러리 · 15초 자동 맞춤
O2 인과 경로음악이 완성 전환율 4% → 60% 달성의 경로로 지목됨

만드는 쪽에는 음악이 필수인데, 보는 쪽에서는 첫 접점에서 소리가 나지 않는다. 사용자가 음악을 골라 완성한 결과물이 피드에서는 무음으로 흐른다.

이건 스파이크로 풀리지 않는다

브라우저 정책이라 실험해도 결과가 바뀌지 않는다. 설계로 대응해야 한다.

#대안효과대가
W1음소거로 시작 + 눈에 띄는 음소거 해제 버튼표준적 · 구현 단순첫 인상에서 음악이 없다
W2첫 조작(탭·스크롤) 시 소리 켜기 — 이후 세션 내 유지한 번만 넘기면 이후 정상첫 한 편은 무음
W3진입 화면에 "소리 켜고 시작" 한 번 묻기명시적 동의로 이후 완전 정상"로그인 화면 없이 바로 재생"(REQ-FUNC-011)의 취지가 흐려진다
W4자막·시각 강조로 무음 전제 설계브라우저 정책과 무관🔴 음악의 가치를 포기 — F18a의 MVP 포함 근거가 흔들린다

W2를 권한다. REQ-FUNC-011의 "로그인 화면 없이 바로 재생" 을 지키면서, 사용자가 어차피 하는 첫 스크롤을 소리 활성화 지점으로 쓴다. 별도 화면도 별도 버튼도 필요 없다.

W4는 피해야 한다. 무음을 전제로 설계하면 "왜 음악 라이브러리에 500곡이 필요한가" 라는 질문이 되돌아온다.

계측 제안 — first_unmute 이벤트를 신설해 무음으로 소비된 비율을 재고, 높으면 W3 전환을 검토한다.

2. S6 — 스파이크는 맞으나 성공 기준이 없다

문제

"Gemini가 사람을 찾아내는가" 는 판정할 수 없는 질문이다. 찾아낸다/못 찾는다의 경계가 없어, 어떤 결과가 나와도 해석이 갈린다.

네 갈래로 쪼개야 한다

#질문실패 시 결과
S6-abbox 좌표를 시계열로 반환하는가🔴 REQ-FUNC-006(구도 보정) 입력이 없다 — 기능 자체가 불가
S6-b가림·재등장 후 동일 인물로 유지하는가🔴 REQ-FUNC-002 불가
S6-c오인식을 측정 가능한 형태로 내놓는가🔴 REQ-FUNC-002의 오인식 ≤ 2% 판정 불가
S6-d40분 길이를 실용적 시간·비용으로 처리하는가🔴 REQ-NF-003 불가

네 개 중 하나라도 실패하면 T1(외부 추론 API)이 정당화된다. 넷 다 통과해야 Gemini 단독 경로가 성립한다.

T1 확정과의 관계

SRS v2.1은 이미 T1을 확정했다(§2.4). 그렇다면 S6은 무엇을 위한 스파이크인가?

S6의 목적이 바뀌어야 한다 — "Gemini로 될까" 가 아니라 "T1의 외부 추론 비용을 Gemini가 일부 대체할 수 있는가" 다.

구체적으로 S6-a·b·c가 실패해도 S6-d와 의미 구간 분류는 쓸 수 있다. SRS v2.1 §7.3이 설계한 후보 생성 보조 경로가 그것이다 — 추적은 외부 API가, "이 구간이 볼 만한가" 는 Gemini가 맡는 분업이다.

이 분업이 성립하면 외부 추론 호출량이 줄어 원가가 내려간다. S6은 실현 가능성 스파이크가 아니라 원가 최적화 스파이크로 재정의해야 한다.

3. F9 폰 용량 회수 — 🔴 지표가 측정 불가능해진다

웹에서 무엇이 막히는가

동작웹비고
사용자 갤러리 파일 삭제🔴 불가브라우저는 단말 파일 시스템에 쓰기 권한이 없다
기기 저장공간 조회🔴 불가오리진 할당량은 알 수 있으나 갤러리 용량은 알 수 없다

지표에 미치는 영향

O4(원본 삭제율 50%)가 웹에서는 측정할 수 없다. SRS §5.4는 O4를 "완성 후 원본 삭제 비율" 로 정의했는데, 그 사건을 관측할 수단이 없다.

선택지

#방향결과
F1안내만 유지 · O4를 자기신고 지표로 재정의기능은 남고 지표 신뢰도가 내려간다. "지웠나요?" 1문항
F2기능을 웹 범위에서 제외 · O4를 네이티브 단계로 이월정직하나 UC-03(저장공간 압박형)의 동기가 웹에서 해소되지 않는다
F3서버 원본 삭제로 대체 — "업로드한 원본을 우리 쪽에서 지웁니다"🔴 다른 문제다. 사용자가 겪는 문제는 폰 용량이지 서버 용량이 아니다

F1을 권한다. F9는 이미 Should Have(P1) 이고, VPS도 O4를 1년차 가설로 뒀다. 자기신고로 방향만 읽고, 정밀 측정은 네이티브 단계로 미룬다.

F3은 문제를 바꿔치기한다. UC-03이 말한 것은 "50분 원본을 못 지운다" 이며 그건 사용자의 폰 안에 있다. 서버에서 지우는 것은 사용자에게 아무 변화가 없다.

🔺 SRS 개정 필요 — O4의 정의를 "완성 후 원본 삭제 비율(자기신고)" 로 바꾸고 측정 방법을 명시해야 한다.

4. S5 브라우저 렌더 — 성공 기준 제안

SRS v2.1 §3.3이 클라이언트 렌더를 전제했으므로 이 스파이크는 설계의 전제를 확인하는 것이다.

#확인기준 제안
S5-aWebCodecs 또는 ffmpeg.wasm으로 15초 세로 숏폼 인코딩이 되는가산출물 재생 가능 · 음악 병합 포함
S5-b소요 시간🔺 단말 등급별로 측정. REQ-NF-004(p95 ≤ 90초)를 등급별로 재정의
S5-c저사양 단말 하한선어느 등급부터 실패하는가 · 실패율
S5-d발열·배터리연속 처리 시 스로틀링 여부

S5-c가 핵심이다. SRS v2.1이 "원가가 0이 되는 대신 성공률이 단말에 종속된다" 고 적었는데, 그 종속의 크기를 모르면 REQ-NF-004를 재정의할 수 없다.

하한선 아래 단말에는 완성 자체가 불가능하므로, 그 경우의 처리(안내 · 서버 대체 경로 · 기능 제한)를 결정해야 한다. 이것도 스파이크가 아니라 결정이다.

5. S2·S3 함수 실행시간 · 토큰 원가 — T1 확정으로 중요도가 내려갔다

이유

T1 확정 전에는 40분 영상 처리가 Vercel 함수 안에서 일어나야 했다. 그래서 실행시간 상한이 치명적이었다.

T1 확정 후 긴 처리는 전부 외부 추론 API로 나갔다. Vercel 함수에 남는 것은 —

작업예상 소요
업로드 개시 · 코덱 검증밀리초
추론 요청 발신밀리초
결과 webhook 수신 · DB 기록밀리초~초
후보 조회 (RSC)밀리초

어느 것도 실행시간 상한에 근접하지 않는다.

S2를 폐기하자는 뜻이 아니다. 값은 알아야 하되 차단 요인이 아니라 참고값으로 내려간다. 우선순위를 S6·S5보다 뒤로 두는 것이 맞다.

S3(토큰 원가)는 성격이 바뀐다

원가 구조가 셋으로 나뉜다.

항목부담 주체관련 요구사항
외부 추론 API (추적)🔴 주 원가REQ-NF-013
Gemini 토큰 (의미 구간)보조 원가REQ-NF-013
렌더사용자 단말 — 0원—

S3만으로는 편당 원가를 산정할 수 없다. 외부 추론 API 단가가 빠져 있다. 🔺 S3에 추론 API 견적을 포함하도록 범위를 넓혀야 REQ-NF-013(편당 원가 상한)의 입력이 완성된다.

6. 탭 종료 시 중단 — SC-1.F4의 의미가 바뀐다

무엇이 달라지는가

SRS SC-1.F4는 "처리 중 앱이 종료되어도 재진입 시 마지막 완료 단계에서 재개" 를 요구한다. 웹에서는 단계마다 성질이 다르다.

단계실행 위치탭 종료 시재개
업로드브라우저 → Storage중단✅ resumable upload로 재개
탐지외부 추론 API🟢 영향 없음 — 서버에서 계속 진행✅ webhook이 DB에 기록
선택브라우저중단✅ 선택 상태가 서버에 있으면 재개
렌더브라우저🔴 소실❌ 처음부터

T1 확정 덕분에 가장 긴 단계(탐지)가 탭 종료에 영향받지 않는다. 이건 설계상 이득이다.

남는 문제는 렌더뿐이다. 15초 결과물 렌더가 수십 초 걸리는데 그 사이 탭을 닫으면 다시 해야 한다.

#방향판단
