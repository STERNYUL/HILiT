# HILiT

> 40분 원본에서 **내가 고른 15초**를 만들고, 올리지 않아도 내 기록으로 남긴다

스포츠(농구 우선) 숏폼 SNS 서비스의 제품 문서 저장소입니다. 현재 단계는 **PRD → SRS 변환**이며, 이 README는 그 변환의 목표·규격·경계를 규정합니다.

## 1. 작업 목표

`PRD/HILiT_PRD_v0.1.md`(PRD v0.1 · 12장 · 1,131행)를 **SRS 형식 문서로 변환**합니다.

### 1.1 무엇을 만드는가

**예시 SRS 문서와 동일한 포맷의 추가 문서를 만든다.**

기준은 SRS 국제 표준안(ISO/IEC/IEEE 29148:2018)의 전체 목차가 아니라 **예시 SRS 문서 그 자체**입니다.

> **예시 SRS 문서와 표준 PDF는 이 저장소에 포함하지 않습니다.** 예시 문서는 사내 양식이고, `29148-2018-ISOIECIEEE.pdf`는 IEEE 라이선스 제한 문서(Authorized licensed use limited to)로 **공개 저장소 배포가 저작권 위반**입니다. 둘 다 `.gitignore`로 제외했으며, 조항 내용은 SRS 본문에 인용 형태로만 반영했습니다.

예시 문서의 **섹션 구성 · 표 서식 · 요구사항 ID 체계 · 기술 밀도**가 곧 변환 규격입니다.

### 1.2 확장 규칙 — 예시 범위를 벗어나는 내용의 처리

기존 PRD에 **예시 SRS의 범위를 벗어나는 내용이 있는 경우에만**, 그 부분에 한해 SRS 표준 포맷의 구성을 따라 확장해 작성합니다.

```
PRD 내용 ─┬─ 예시 SRS에 대응 절이 있음  →  예시 포맷 그대로 이관
          └─ 예시 SRS에 대응 절이 없음  →  그 부분만 29148 조항 근거로 확장
```

확장은 **예외 처리**입니다. 기본값은 언제나 예시 포맷이며, 확장은 **옮길 그릇이 없는 내용에만** 적용합니다.

### 1.3 비목표 (Non-goals)

| 하지 않는 것 | 이유 |
| --- | --- |
| SRS 표준안 풀버전 문서 작성 | 목표는 예시 포맷 준수. 표준 전체 목차를 채우는 것이 아님 |
| 예시 SRS에 없는 절을 표준 목차대로 일괄 신설 | 확장은 PRD에 옮길 내용이 실제로 있을 때만 |
| PRD 내용의 신규 추가·창작 | **변환이지 집필이 아님.** 없는 요구사항을 만들지 않음 |
| PRD·VPS 원본 수정 | 상위 문서로 보존. SRS는 별도 산출물 |
| 팀 SRS의 요구사항 ID 재번호 | 이미 확정된 추적성 매트릭스가 끊어짐 (2.3 참조) |

## 2. 변환 규격

### 2.1 절 구성 — 예시 7개 절 보존, 확장 9개 항목

```
1. Introduction         1.1 Purpose / 1.2 Scope / 1.3 Definitions  ← 예시
                        [1.4 References] [1.5 Constraints] [1.6 Assumptions]
2. Stakeholders         2.1 이해관계자  ← 예시
                        [2.2 이용자 클래스 및 특성]
3. System Context       3.1 External Systems / 3.2 Client Applications
                        3.3 API Overview  ← 예시
                        [3.4 Interaction Sequences]
4. Specific Requirements 4.1 기능 / 4.2 비기능  ← 예시 (9열 표 그대로)
                        [4.3 요구사항 의존성 및 구현 규모] [4.4 표준 및 규제 준수]
5. Traceability Matrix  5.1 Story ↔ REQ ↔ TC  ← 예시
                        [5.2 REQ ↔ 측정 지표]
6. Appendix             6.1 API / 6.2 Entity & Data Model  ← 예시
                        [6.3 Detailed Interaction Models] [6.4 Validation Plan]
                        [6.5 차별점 근거] [6.6 미해결 사항]
```

`[ ]` = 확장 (9개 항목). 예시의 절 **정체성은 전부 보존**됩니다.

### 2.2 확장 절의 표준 근거

확장 절은 임의로 만들지 않고 **ISO/IEC/IEEE 29148:2018 조항에 1:1로 근거**를 둡니다. §9.6.1이 "절 구성 순서는 프로젝트 정보관리 정책에 따라 선택할 수 있다"고 허용하므로, 사내 양식의 절 구성을 유지한 채 대응 절이 없는 내용만 조항 근거로 확장했습니다.

| 확장 절 | 근거 조항 |
| --- | --- |
| 1.4 References | §9.6.2 References |
| 1.5 Constraints | §9.6.7 Limitations · §9.6.16 Design constraints |
| 1.6 Assumptions | §9.6.8 Assumptions and dependencies |
| 2.2 이용자 클래스 및 특성 | §9.6.6 User characteristics |
| 3.4 Interaction Sequences | §9.6.4 블록 다이어그램 · §9.6.5 b) 기능 관계 도해 |
| 4.3 요구사항 의존성 및 구현 규모 | §9.6.9 Apportioning of requirements |
| 4.4 표준 및 규제 준수 | §9.6.17 Standards compliance |
| 5.2 REQ ↔ 측정 지표 | §9.6.9 (교차 참조표 요구) |
| 6.4 Validation Plan | §9.6.19 Verification |

**대응 내용이 없는 조항은 채우지 않았습니다.** §9.6.4.3(하드웨어 인터페이스)은 전용 장비를 쓰지 않는 것이 이 제품의 차별점이라 해당 없음이며, §9.6.4.6(메모리 제약)은 자원 제약이 메모리 용량이 아니라 **GPU 처리량과 편당 단가**로 표현되어 REQ-NF-013으로 대체했습니다.

조항이 부과한 규율도 따랐습니다.

- **§9.6.6** "이용자 특성 절에 구체적 요구사항을 명시하지 말라" → 2.2는 대응 REQ ID만 참조
- **§9.6.19** "검증 항목은 §9.6.10~18과 병렬로 제시" → 6.4가 4.1·4.2의 `검증 방식` 열과 병렬 구조
- **§9.6.20** "이 정보 항목이 요구사항의 일부인지 명시하라" → **1.1·6.5는 배경 정보이며 요구사항이 아님**을 본문에 명시

**단일성(§5.2.5 Singular)** — "요구사항은 단일 능력·특성·제약·품질 인자를 진술한다"에 따라 **이행 수단이 서로 다른 통제는 분리**했습니다(업로드/이어올리기/코덱검증, 대상지정/재식별, 암호화/접근통제). 반면 **하나의 인자를 여러 지표로 측정하는 경우는 유지**했습니다.

### 2.3 팀 SRS와의 통합 — ID를 재번호하지 않는다

팀이 이미 `hilit-srs-v1_0.html`(v1.0 확정판 · REQ 41건 · 추적성 매트릭스 30건)을 확정했습니다. **ID를 재번호하면 그 매트릭스와 테스트 케이스 ID가 전부 끊어집니다.**

| 구간 | 처리 |
| --- | --- |
| REQ-FUNC-001~026 · REQ-NF-001~015 | 팀 v1.0의 **식별자와 의미를 손대지 않고 보존** |
| REQ-FUNC-027 · REQ-NF-016 · 017 | **승격 3건** — 팀 §4·§11·API 어디에도 없던 것만 |
| SC-0.1 · 0.F1 · 1.F4~F6 · 3.F2 · 4.5 · 4.F2 | **시나리오 신설 9건** |

**요구사항을 늘리는 대신 검증 가능성만 얻습니다.**

v1.1~v1.2는 실패 경로를 요구사항으로 승격해 REQ를 41 → 60건으로 늘렸습니다. 그러나 **그중 17건은 팀 SRS의 §11 운영 시나리오와 API 설명에 이미 있었습니다.**

진짜 문제는 요구사항의 부재가 아니라, **운영 시나리오가 §5 추적성 매트릭스에 행이 없어 테스트 케이스 ID가 붙지 않는다**는 것이었습니다. 그래서 `TC-FUNC-001`이 코덱 거부 케이스를 포함했는지 문서로 확인할 수 없었습니다.

**v1.3은 그 구멍만 막습니다.** 시나리오 38건과 설계 결정 3건에 TC ID를 부여해 매트릭스에 넣었습니다. 요구사항 승인 절차를 다시 밟을 필요가 없고, 팀 입장에서는 *"요구사항이 19개 늘었다"* 가 아니라 *"기존 시나리오에 번호가 붙었다"* 가 됩니다.

| 구간 | v1.2 | v1.3 |
| --- | ---: | ---: |
| 요구사항 | 60 | **44** (팀 41 + 승격 3) |
| 운영 시나리오 | — | **42** (팀 33 + 신설 9) |
| 설계 결정 검증 | — | **3** |
| **매트릭스 총 행** | 60 | **89** |

**승격 판정 기준** — ① 팀 §4·§11·API 어디에도 없는가 ② 부모 요구사항과 **담당자가 다른가** ③ 없으면 리스크 대응 수단이 사라지는가. **셋 중 둘 이상**이면 승격합니다. 이 기준으로 19건 중 2건만 남았습니다.

### 2.4 표기 규칙 — 모든 숫자는 출처 상태를 갖는다

| 태그 | 뜻 |
| --- | --- |
| `[SOURCE]` | VPS 0.3에 **직접 명시**된 값 |

| `[TBD]` | 추가 의사결정이 필요한 미정 상태 |

**세 가지를 금지합니다.**

| # | 금지 | 이유 |
| --- | --- | --- |
| **N1** | 경쟁사 대비 배수·퍼센트 | "탐지율 2배"는 **측정된 적 없는 분모**를 전제한다. 원 주장은 범주적("조사한 목록에 없다")이며 그쪽이 더 강하다 |
| **N2** | 판정할 수 없는 문장을 요구사항으로 쓰기 | "법무 검토 선행 필수"는 통과/실패를 판정할 수 없다. **산출물 승인 = 배포 게이트**로 바꿔야 CI가 판정한다 |
| **N3** | 기준선 빈칸을 그럴듯한 숫자로 메우기 | 없는 숫자 대신 **언제·무엇으로 확정할지**를 적는다. 상위 문서가 대시로 둔 칸은 대시로 남긴다 |

## 4. 지금 상태에서 가장 중요한 것

**미해결 13건 중 해소 순서가 정해져 있습니다.** 근거는 소요 시간이 아니라 ① 전복 가능성 ② 차단성 ③ 되돌리는 비용입니다.

| 순위 | 항목 | 왜 이 자리인가 |
| :--: | --- | --- |
| **0** | **Q12 — 국내 기초 설문** (농구 동호회 100명 · 문항 2개) | 유일하게 **문제 정의 자체를 무효로** 만들 수 있다. 가장 싸고 독립적이다 |
| **1a** | **Q1 — 재식별 오탐률 지표 정의** | Gate A를 설계할 수 없다. 합의 문제라 비용이 낮아 **0순위와 병렬** |
| **1b** | 정답셋 구축 | 비용이 큰 쪽. **0순위가 뒤집히면 통째로 낭비** |
| **2** | **Q11 — 확장 종목 결정** | VPS가 시점을 **"Gate A 통과"**로 이미 못 박았다. 지금 정하면 순서 위반 |

> Q1은 *"만들 수 있는가"*를 묻고, Q12는 ***"만들 이유가 있는가"***를 묻습니다.
> **가장 싸게 사업을 부정할 수 있는 검증을 먼저 돌립니다.**

**Gate A가 모든 것의 앞에 있습니다.** 등장 구간 탐지율이 85%에 미달하면 나머지 요구사항은 일반 기록 앱이 됩니다 — 이것이 RISK-01을 치명으로 판정하고 Gate A를 최우선·단독으로 배치한 근거입니다.

## 5. 문서 변환

`.md` ↔ `.html` 변환에 사용한 스크립트는 저장소에 포함하지 않습니다. 변환 결과만 커밋합니다.

- **Markdown → HTML** : 표 · mermaid · 코드 펜스 · 목차 자동 생성. 라이트/다크 테마 대응
- **HTML → Markdown** : 표 · 목록 · 시퀀스 다이어그램 보존
