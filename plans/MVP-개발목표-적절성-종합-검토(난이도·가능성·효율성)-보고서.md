# 0. 요약

## 0.1 판정

| 관점 | 판정 | 핵심 |
| --- | :--: | --- |
| **① 개발 속도** | 🟡 **조정 필요** | 스택 선택은 속도에 유리하나, **MVP 17개 중 셋이 법무 대기에 묶여 있다** |
| **② 외부 연동·스택** | 🟢 **적절** | 외부 의존이 4개로 적고 전부 대체 가능. **단 추론 API만 대체가 어렵다** |
| **③ 운영 비용** | 🔴 **재산정 필요** | **전송 비용이 누락돼 있다** — 원가 구조가 3분할이 아니라 4분할이다 |

## 0.2 🔴 이 검토의 가장 큰 발견 셋

### 발견 1 — 원가 구조에서 **전송 비용이 빠져 있다**

SRS v2.2는 편당 원가를 **추론 API + Gemini + 단말(0원)** 셋으로 나눴다. **그러나 4GB 원본을 추론 API로 넘기는 전송 비용이 없다.**

연 12만 편 × 4GB = **연 480TB의 외부 전송**이다. 클라우드에서 egress는 통상 가장 비싼 항목이며, 이것이 **추론 원가를 넘을 가능성**이 있다.

→ **§3.2** · REQ-NF-013 재정의 필요

### 발견 2 — ADR-3이 **전송 비용도 줄인다**

`저해상도 1차 → 선택분만 고화질`(ADR-3)의 근거는 지금 **GPU 원가**만 적혀 있다. 그러나 **저해상도로 전처리해 넘기면 전송량도 함께 준다.**

**그런데 다운스케일은 탐지율을 떨어뜨린다** — 원거리에서 인물이 작게 잡히는 것이 이 제품의 조건이기 때문이다. **전송비와 O9가 같은 손잡이에 걸려 있다.**

→ **SP-1에 B8(입력 해상도별 탐지율) 항목 추가 필요**

### 발견 3 — **공개 발행을 MVP에서 빼면 법무 대기가 사라진다**

현재 MVP는 **REQ-NF-010(얼굴 4종) · REQ-NF-017(미성년자 3종) · REQ-FUNC-007(음원 3종)** 세 게이트에 묶여 있고, 앞의 둘은 **공개 발행 기능을 차단**한다.

**Core Job은 *"공개와 무관하게 내 기록으로"* 다. 공개 발행이 없어도 Core Job·D4·Gate B가 전부 성립한다.**

→ **§1.3** · MVP 범위 조정안

# 1. 개발 속도

## 1.1 규모 판정 재확인

| 규모 | 건수 | 대상 |
| :--: | ---: | --- |

## 1.3 🔴 속도를 위협하는 것 넷

### ① 클라이언트 렌더 — **가장 큰 시간 위험**

| 항목 | 판단 |
| --- | --- |
| 대상 | REQ-FUNC-008 (M) |
| 위험 | WebCodecs·ffmpeg.wasm은 **브라우저·기기별 편차가 크고 디버깅이 어렵다** |
| 실제 규모 | 🔴 **M이 아니라 L에 가깝다** — 종료 조건이 *"동작한다"* 가 아니라 *"어느 단말까지 되는가"* 다 |

> **SRS §4.3의 L 정의는 *"모델 성능이 결과를 좌우"* 였다.** 클라이언트 렌더는 **단말 성능이 결과를 좌우**하므로 같은 성질이다. **규모 판정을 M → L로 올리고 Gate A 트랙과 같은 방식(측정 주기)으로 다뤄야 한다.**
>
> → 🔺 **SRS §4.3 규모 재판정 필요**

### ② RLS 정책 — 강력하나 검증이 무겁다

REQ-NF-009는 *"조작된 요청의 우회 성공 0건"* 을 요구한다. **RLS는 작성보다 검증이 오래 걸린다** — 정책이 의도대로 막는지, 의도한 것까지 막아버리진 않는지를 조회 경로마다 확인해야 한다.

**다만 이것은 스택 때문에 생긴 비용이 아니다.** 일반 백엔드로 만들면 같은 검증을 **애플리케이션 코드 전수**에 해야 한다. RLS가 오히려 검증 지점을 한 곳으로 모은다.

### ③ 🔴 음악 라이브러리 — **개발이 아니라 계약이 병목**

REQ-FUNC-007(M)의 기술 난이도는 낮다. **그러나 라이선스 계약 없이는 곡이 0개이므로 기능이 성립하지 않는다.**

**개발 속도와 무관하게 Phase 1을 막는다.** 계약 협의는 개발자가 앞당길 수 없다.

### ④ 🔴 법무 게이트 셋 — MVP 경로 위에 있다

| 게이트 | 차단 대상 | 산출물 |
| --- | --- | :--: |
| REQ-NF-010 | **공개 발행 · 그룹 공개** | 4종 |
| REQ-NF-017 ③④ | **공개 발행 · 그룹 공개** | 3종 |
| REQ-FUNC-007 | 음악 라이브러리 | 3종 |

**셋 다 개발이 아니라 승인 대기다.** 개발이 끝나도 승인이 안 나면 기능이 빌드에 들어가지 않는다.

## 1.4 🔴 MVP 범위 조정안

> **질문 — 17개가 정말 전부 MVP여야 하는가.**

### 근거: VPS의 논리를 그대로 적용하면

VPS는 F14(선택 데이터 학습)를 **"사용자 없이는 학습 데이터가 생기지 않는다"** 는 이유로 유보했다. **같은 논리가 반응 기능에도 적용된다** — 사용자가 열 명일 때 좋아요·댓글이 붙을 대상이 없다.

**그러나 VPS의 반론도 유효하다** — *"관계망은 나중에 붙일 수 없다."* 이건 사실이다. 다만 **관계 구조와 반응 기능은 다르다.**

| 구분 | 나중에 붙일 수 있나 | 판단 |
| --- | :--: | --- |
| F11 팔로우 · F13 피드 · F23 그룹 | 🔴 **어렵다** — 데이터 모델과 조회 경로의 뼈대 | **Day-1 유지** |
| F19 좋아요 · F20 댓글·신고 · F21 공유 | 🟢 **쉽다** — 기존 기록에 얹는 기능 | **조정 가능** |

### 제안 — 공개 발행을 Phase 3에서 분리

| 안 | 범위 | 효과 |
| --- | --- | --- |
| **현행** | MVP 17 (그룹 공개 + 전체공개 + 반응 3종) | 법무 게이트 3개 전부 MVP 경로 |
| 🔵 **조정안** | MVP 14 (**그룹 공개까지** · 반응 3종 후속) | 🟢 **REQ-NF-010·017 게이트가 MVP 경로에서 빠진다** |

**Core Job 점검** — *"이미 찍어둔 / 내가 판단한 / 공개와 무관하게 내 기록으로"*. **공개 발행이 없어도 세 조건 전부 성립한다.** D4(기록 우선·공개 선택)도 성립하고 **Gate B(기록 공간이 부계정을 대체하는가)** 도 그대로 판정된다.

**잃는 것** — O7(재방문) 검증이 약해진다. 다만 **그룹 공개만으로도 소비 루프의 최소 형태는 돈다.**

> 🔺 **이건 기술 판단이 아니라 제품 결정이다.** 다만 **얻는 것이 크다** — 법무 승인 대기가 MVP 완주 경로에서 빠지고, 미성년자 영상 처리 부담도 파일럿 수준으로 낮아진다.

# 2. 외부 연동과 기술 스택 적절성

## 2.1 외부 의존 목록

| # | 대상 | 성격 | 오픈소스 대체 | 잠금 위험 |
| :--: | --- | --- | :--: | :--: |
| 1 | **Vercel** | 배포·실행 | 🟢 가능 (Node 호스팅 일반) | 🟢 낮음 |
| 2 | **Supabase** | DB·스토리지·인증·Realtime | 🟢 **오픈소스** · 자체 호스팅 가능 | 🟢 낮음 |
| 3 | **Gemini** | 영상 이해 | 🟡 SDK 추상화로 교체 가능 (C-TEC-006) | 🟡 중간 |
| 4 | 🔴 **추론 API** | 인물 추적 | 🟡 **모델은 오픈소스(SAM 2)이나 호스팅은 종속** | 🔴 **높음** |
| 5 | 음원 제공자 | 라이선스 | 🔴 대체 어려움 | 🟡 중간 |
| 6 | 카카오 공유 | 전달 | 🟢 OS 공유 시트로 대체 | 🟢 낮음 |

**여섯 중 넷은 잠금 위험이 낮다.** Supabase는 오픈소스라 최악의 경우 자체 호스팅이 되고, Vercel도 Next.js 자체는 다른 호스팅에서 돈다.

## 2.2 🔴 추론 API만 성격이 다르다

| 항목 | 판단 |
| --- | --- |
| 대체 가능성 | 🟡 **모델(SAM 2)은 오픈소스** — 그러나 **직접 호스팅하면 C-TEC-005 위반**이자 T1이 피하려던 운영 부담이 돌아온다 |
| 잠금의 실체 | **API 스펙이 아니라 정확도 특성**에 잠긴다. 다른 API로 바꾸면 O9·오탐률이 달라지고 **Gate A를 다시 통과해야 한다** |
| 완화 | 🔺 **추상화 계층 필수** — Gemini와 같은 방식(§2.3) |

> **이것이 이 아키텍처의 유일한 실질 잠금이다.** 그리고 SP-1이 그 대상을 고른다.

## 2.3 🔺 권고 — 추론 API도 SDK 수준으로 추상화

C-TEC-006은 **Gemini만** 환경 변수 교체를 요구한다. 그런데 **바꿀 가능성이 더 높은 것은 추론 API**다(SP-1 후보가 둘이고, Gate A 결과에 따라 갈린다).

```ts
// lib/inference/provider.ts
export interface TrackingProvider {
  submit(input: { videoUrl: string; anchor: BBox; frameMs: number; callbackUrl: string })
    : Promise<{ inferenceId: string }>;
  parseWebhook(body: unknown): { intervals: Interval[]; confidence: number[] };
}
```

**두 후보(AWS · Replicate)의 응답 형태가 다르므로 어댑터가 필요하다.** SP-1 벤치마크 코드를 이 인터페이스로 짜면 **벤치마크 하니스가 그대로 프로덕션 어댑터가 된다.**

## 2.4 복잡성 평가

| 항목 | 평가 |
| --- | :--: |
| 서비스 개수 | 🟢 **적절** — 단일 앱 + 외부 6 |
| 계층 수 | 🟢 적절 — 프론트/백 미분리로 오히려 단순 |
| 비동기 경로 | 🟡 **주의** — 업로드 → 추론 → webhook → Realtime의 4단 비동기. **상태 추적이 이 시스템의 복잡성 중심** |
| 데이터 일관성 | 🟢 단일 PostgreSQL |

> **복잡성은 서비스 개수가 아니라 비동기 경로에 있다.** ProcessingJob의 `stage`·`checkpoint`가 그 복잡성을 흡수하도록 설계돼 있고(DS §6 상태 기계), 이 설계가 없으면 디버깅이 어려워진다.

## 2.5 외부 연동 종합 — 🟢 **적절**

**외부 의존이 적고 대부분 대체 가능하다.** 유일한 실질 잠금은 추론 API이며, **추상화 계층으로 완화 가능**하다.

# 3. 운영 비용

## 3.1 산정 전제

| 항목 | 값 | 출처 |
| --- | ---: | --- |
| 연 처리 물량 | **12만 편** | 1만 명 × 월 1편 `[HYPOTHESIS]` |
| 원본 크기 | **4GB** / 40분 | `[SOURCE]` |
| 결과물 크기 | 약 5MB / 15초 | `[추정]` |
| 원본 보관 | **결과물 확보 시점까지** | 비즈니스 규칙 9 |

## 3.2 🔴 원가 구조 — 3분할이 아니라 **4분할**

| # | 항목 | 규모 | 현재 문서 |
| :--: | --- | --- | :--: |
| 1 | **추론 API** | 편당 × 12만 | ✅ 반영 |
| 2 | Gemini 토큰 | 편당 × 12만 | ✅ 반영 |
| 3 | 렌더 | **0원** (사용자 단말) | ✅ 반영 |
| **4** | 🔴 **저장 + 전송** | **아래 참조** | ❌ **누락** |

### 전송량 계산

```
업로드 (사용자 → Storage)      4GB × 12만 =  480TB/년   ← 통상 무료 또는 저렴
추론 API로 전달 (Storage → 외부) 4GB × 12만 =  480TB/년   ← 🔴 egress · 통상 유료
결과물 배포 (Storage → 시청자)   5MB × 12만 × 조회수      ← 소비 루프에 비례
```

> 🔴 **`Storage → 추론 API`의 480TB가 지금 어느 문서에도 없다.**
>
> 클라우드에서 **egress(외부 전송)는 통상 가장 비싼 항목**이다. 정확한 단가는 사업자·리전·계약에 따라 다르므로 여기 적지 않으나, **480TB는 무시할 수 없는 규모**이며 **추론 원가를 넘을 가능성이 있다.**

### 저장량

원본을 **결과물 확보까지만** 보관하면 상시 저장량은 처리 중인 분량으로 한정된다.

```
주당 처리 ≈ 12만 / 52 ≈ 2,300편
동시 보관 ≈ 2,300 × 4GB ≈ 9.2TB   ← 보관 기간 1주 가정 [추정]
```

**보관 기간이 원가를 선형으로 좌우한다.** 🔺 REQ-NF-014의 *"보존 기간 `[TBD]`"* 가 비용 항목이기도 하다는 점이 명시돼 있지 않다.

## 3.3 🔴 ADR-3의 근거를 넓혀야 한다

ADR-3(`저해상도 1차 → 선택분만 고화질`)의 현재 근거는 **GPU 원가**뿐이다. **그러나 저해상도로 전처리해 넘기면 전송량도 함께 준다.**

| 전처리 | 전송량 (연) | 효과 |
| --- | ---: | --- |
| 원본 그대로 | 480TB | 기준 |
| 1/2 해상도 | 약 120TB `[추정]` | 🟢 **4분의 1** |
| 1/4 해상도 | 약 30TB `[추정]` | 🟢 **16분의 1** |

### 🔴 그런데 여기에 상충이 있다

**다운스케일은 탐지율을 떨어뜨린다.** 이 제품의 조건이 *"코트 반대편에서 화면 구석에 작게"* 이므로, **원거리 인물은 다운스케일에 특히 취약하다.**

> **전송비와 O9가 같은 손잡이에 걸려 있다.** 해상도를 낮추면 비용이 제곱으로 줄지만 탐지율도 함께 떨어진다.
>
> **→ SP-1 벤치마크에 항목 추가가 필요하다.**

### 🔺 SP-1 추가 항목 — B8

| # | 항목 | 측정 |
| :--: | --- | --- |
| **B8** | **입력 해상도별 탐지율** | 원본 · 1/2 · 1/4 각각에서 B1(탐지율)·B2(오탐률) 측정 |

**이 값이 나와야 "탐지율을 얼마나 포기하면 전송비를 얼마나 아끼는가"를 계산할 수 있다.** 지금은 그 교환비를 모른 채 ADR-3을 적용하고 있다.

## 3.4 Vercel 실행 비용

**T1 확정으로 함수 실행 시간이 밀리초 단위로 줄었다.** 업로드 개시·추론 요청·webhook 수신·후보 조회가 전부 짧다.

| 항목 | 판단 |
| --- | :--: |
| 함수 실행 | 🟢 **미미** |
| 대역폭 | 🟡 결과물 배포가 Vercel을 거치면 비용 발생 → **Storage 직접 서빙 권고** |

> 🔺 **결과물을 Vercel을 통해 서빙하지 않는다.** Signed URL로 Storage에서 직접 내보내야 한다. 피드가 도는 만큼 이 경로가 반복된다.
